# DuckDB as a first-class part of night-watchman

Research note, 2026-09-15, branch `research/duckdb`. This is an
explanation doc: it argues a position. Nothing here is implemented. The
owner asked whether DuckDB should ship as part of the suite itself, not as
a provider or plugin.

Confluence was the first choice for this write-up. The Atlassian
connector returned `403 "The app is not installed on this instance"` for
Confluence (the token only has Jira scopes), so the note lives here.

## Verdict

**Not now as a core dependency.** Use it as an optional analytics tool
the suite detects when present, never as a requirement. Revisit when one
of the triggers under [When to revisit](#when-to-revisit) fires.

DuckDB is a good engine and fits the shape of our data well. It is also
the wrong size for the problem we have today. The suite's data is small.
The hard parts of our transcript mining are procedural heuristics, not
aggregation. And the core install promise is "dependency-free core only"
(README.md). A 62 MB binary with no apt package breaks that promise to
speed up queries that already finish in about 40 ms.

The owner's framing ("part of our suite, not a plugin") still fits an
optional tool. jq already works this way in `scripts/parity-sweep.sh`:
the script checks `command -v jq` and falls back when jq is missing. An
optional DuckDB would be the same kind of thing, owned by the suite and
documented by the suite, but not needed to install or run it.

## What DuckDB is for

DuckDB is an in-process OLAP (analytics) SQL engine, often described as
"SQLite for analytics". It has no server. It runs inside the calling
process or as a single CLI binary, and it can query CSV, JSON,
newline-delimited JSON and Parquet files in place with SQL, including
globs across many files ([loading JSON][loadjson]).

Its design goals and non-goals, from its docs:

- **Good for:** column-oriented aggregation, joins and window functions
  over local files; ad-hoc analysis; converting between CSV, JSON and
  Parquet.
- **Not for:** OLTP workloads with many small concurrent writes; several
  processes writing one database file (a second read-write process gets
  "already opened by another process"); client-server access.
  Sources: [concurrency][conc], [why DuckDB][why] (secondary summary:
  [endjin][endjin]).

## Where the suite processes data today

Inventory at this commit, grouped by what each site really does.

### 1. Transcript and event analytics (Python stdlib)

| File | Size | What it does |
| --- | --- | --- |

| `scripts/claude-cost-scan.py` | 346 lines | Scans `~/.claude/projects/<slug>/**.jsonl`, dedups streamed lines by `message.id`, prices tokens. |

`cost-reviewer` calls these scripts. `reflector` reads the transcript

### 2. HTTP API response shaping (jq)

### 4. Everything else

`parity-sweep.sh` walks settings JSON with jq when present.
`skills/to-issues/scripts/issues.py` parses Markdown frontmatter. Neither
is tabular analytics.

## Where DuckDB would and would not help

### Group 1: analytics. Real fit, low payoff today

What fits. The events file, the ledger and the transcripts are exactly
the files DuckDB is built to query. Measured on this machine (Ubuntu
26.04, DuckDB 1.5.5 CLI in a scratch directory):

- One SQL query reproduced `claude-cost-scan.py`'s dedup and token totals
  on the first attempt: opus 565,536 tokens and sonnet 151,141 tokens,
  identical to the Python output.
- Schema inference over every local transcript worked with no schema
  written by hand (`union_by_name=true`).
- A `lag()` window over the TSV ledger replaces the delta math in
  `claude-cost.py compare` in one line.
- Cross-file joins become cheap to write. Examples: per-ticket cost next
  to owner-wait seconds next to status durations; script usage against
  author cost. Today each of these is a new Python function.
- Agent token cost may drop. An agent can ask one aggregate question in
  SQL instead of reading raw JSONL, which fits "expensive model decides,
  cheap model reads". It also enforces `cost-reviewer`'s rule to print
  aggregates only, never raw content. (Assumption, not measured.)

Why the payoff is low:

- **Scale.** The whole local transcript store is 4.6 MB in 12 files, none
  over 10 MB. `claude-cost-scan.py` takes about 40 ms. DuckDB took about
  35 ms and used a 50 MB resident set. Speed is not a problem we have.
- **The hard logic is not SQL-shaped.** Most of `script-analytics.py`'s
  2,759 lines are heuristics: splitting shell commands into segments to
  find `scripts/*.sh` in an executable position, unioning `tool_use`
  blocks across lines that share one `message.id`, slicing a transcript
  at each SendMessage resume prompt, and matching `HUMAN_STEP_RE`. These
  stay procedural in any language. SQL would replace the `report`
  aggregation (roughly the last fifth of the file), not `extract`.
- **Rewrite cost is real.** The Python has selftests with fixtures
  (`script-analytics-selftest.sh` is 79 KB). Porting means rebuilding
  that coverage for a second implementation of the same numbers.

### Group 2: API response shaping. No fit

One response at a time, built and read inside a request loop. jq is the
right tool. DuckDB adds a process start and SQL for a job that is a field
lookup.

### Group 3: hook stdin parsing. Must not use DuckDB

Hooks run on every tool call and must fail open. Adding a 62 MB binary to
that path adds startup cost and a new failure mode to every tool call, for
no gain over jq.

## Cost of adding a binary dependency

| Concern | Finding |
| --- | --- |
| Install promise | README.md: both install forms "install the dependency-free core only". Today the floor is bash 3.2, jq, and Python 3 stdlib. DuckDB would be the first downloaded binary. |
| Binary size | Linux amd64 CLI: 21 MB zip, 62 MB unpacked (measured). PyPI wheel: 15.5 MB to 21.5 MB depending on platform ([PyPI][pypi]). |
| macOS | `brew install duckdb` ([Homebrew][brew]). Stock macOS has no DuckDB, so a Homebrew-less Mac needs the install script or a release zip. Wheel tags suggest macOS 11 (arm64) and 10.15 (x86_64) minimums (unverified). |
| Ubuntu | Not in Ubuntu's archive: `apt-cache policy duckdb` is empty on Ubuntu 26.04 (measured). Options are the install script `curl -sL https://install.duckdb.org \| sh` ([install][install]), the Snap ([snap][snap]), or a GitHub release zip. |
| glibc | The 1.5.5 Linux binary needs `GLIBC_2.25` and `GLIBCXX_3.4.22` symbols (measured with `objdump -T`). A secondary source says 2.28; the measured figure is the tighter fact. |
| Architectures | Linux, macOS and Windows on x86_64 and arm64 ([install][install]). |
| Python route | `pip install duckdb` needs Python 3.10 or newer ([PyPI][pypi]). It breaks the stdlib-only rule for `scripts/*.py` in `docs/cost.md`. |
| bash 3.2 | Not affected. The CLI takes `-c`, `-csv`, `-json`, `-markdown` and reads `/dev/stdin`, so a bash 3.2 script can call it like jq. |
| Selftests | Selftests would need DuckDB on every CI and dev machine, or a skip path. A skip path means the DuckDB code runs untested wherever it is absent. |

| Fact | Value | Source |
| --- | --- | --- |
| Licence | MIT, same as night-watchman | [duckdb.org][home] |
| IP holder | Non-profit DuckDB Foundation. DuckDB Labs is the commercial company run by the creators. | [FAQ][faq] |
| Ownership change | Press reports say AWS acquired DuckDB Labs around August 2026, with the Foundation keeping the IP. **Unverified**: secondary press only. | [cryptonomist][aws] |
| 1.0 and storage compatibility | Since v0.10 (2024-02) every version reads files written by older versions. Newer files in older versions are best effort only. | [storage][storage], [0.10][v010] |
| Latest stable | 1.5.5, 2026-07-22 (measured download matches) | [release calendar][cal] |
| LTS | Every other minor release is LTS, with about one year of community support. 1.4 LTS community support ends 2026-09-16. The next release, 2.0.0 LTS, is planned for about 2026-10-21. | [1.4.5][v145], [release calendar][cal] |
| Security | CVE-2026-58139 in the `aws` extension (credential leak, CVSS 6.5). The npm `duckdb` bindings shipped malware in a supply-chain attack; the CLI and Python packages were not affected. No 2026 CVE against the core engine found. | [CVE][cve], [GHSA][ghsa] |

Maturity is not the blocker. Timing is awkward: pinning today means
either a non-LTS 1.5 line or an LTS line whose support ends tomorrow,
with a major version due in about five weeks.

## Pitfalls found while testing

Each of these was reproduced in the scratch directory. Any future DuckDB
code in this repo needs a guard for each one.

1. **`ignore_errors=true` turns bad lines into NULL rows. It does not
   skip them.** A four-line file with one `not json` line returned four
   rows, one of them all NULL. The ledger code does the opposite: it
   refuses a truncated last line loudly. Count and reject NULL rows
   explicitly, or leave `ignore_errors` off and fail.
2. **Type drift changes the column type.** One `"a": "three"` among
   integers silently turned column `a` into `json`. Declare column types
   for any file whose schema is a contract (the ledger, the events file).
3. **Money comes back as floating point.** `1.2 - 1.5` printed
   `-0.30000000000000004` until the column was read as `DECIMAL(12,4)`.
4. **`enable_external_access=false` also blocks local files.** Pair it
   with `allowed_directories=[...]` and `lock_configuration=true`. With
   that set, a read outside the allowed directory and a remote URL were
   both refused.
5. **Extension autoload tries the network.** A query on an `https://` URL
   tried to download `httpfs` into `~/.duckdb/extensions/`. The `json`,
   `parquet` and `icu` extensions are compiled into the CLI, so set
   `autoinstall_known_extensions=false` and
   `autoload_known_extensions=false` for offline and selftest runs. This
   matches the "structural network isolation in selftests" rule in
   `skills/shell-scripting`.
6. **CLI regressions happen between minors.** An open issue reports that
   `-jsonlines` and JSON on `/dev/stdin` broke in the 1.5 CLI
   ([#21464][i21464], unverified). Pin a version and test the exact flags
   used.
7. **Transcripts are live files.** The session writes its own transcript
   while a query reads it. Reading was fine here, but results are a
   snapshot, same as the Python scanner.

## What DuckDB should not be used for

- Hooks, or anything else on the per-tool-call path.
- The source of truth for the ledger or the events file. Those stay
  append-only text files that bash, Python and a log shipper can read.
  A `.duckdb` database file would add a single-writer lock that parallel
  worktree agents would hit.
- Jira, Confluence or herdr API request and response shaping.
- Ticket frontmatter, docs linting, or `reflector`'s reading of prose.
- Any path a fresh adopter needs on day one.

## If the owner wants a step anyway

Following ethos row one, "ship the smaller, reversible option first":

1. One read-only script, for example `scripts/nw-query.sh`, that runs a
   named, version-pinned SQL file from `scripts/sql/` over the ledger,
   events file or transcripts. It detects `duckdb` with `command -v`,
   exits `2` with an install hint when absent, and always sets the
   lockdown options in pitfalls 4 and 5.
2. `cost-reviewer` may use it for cross-file questions. It keeps the
   Python scripts as the numbers of record.
3. Nothing in `hooks/`, `providers/` or the install path changes.

Removing that is one script and one directory. Filing it as a ticket is
the owner's call; this note does not file one.

## When to revisit

Revisit a core dependency when any of these happens:

- The Python scanner or `report --usage` takes more than a few seconds
  on a real adopter's data, for example team-wide or months of
  transcripts in the hundreds of MB.
- `cost-reviewer` needs a new cross-file join for a third wave in a row
  (a repeated-work signal under `skills/capability-ladder`).
- An adopter wants Parquet exports or dashboards over the events file.
- DuckDB 2.0 LTS has shipped and had a few patch releases.
